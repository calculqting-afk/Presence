# Cloudflare admin password reset

The same Worker also supports protected dashboard Student ID corrections. See [ID correction and activity history](ADMIN-ID-AND-ACTIVITY.md) for the two additional IAM permissions, preview-signing secret and independent feature flag. Password resets refuse accounts with a pending ID correction lock.

Worker: `https://presence-admin-api.mikhailovna2007.workers.dev`. Configuration and server code live in `workers/admin-api/` and are excluded from Firebase Hosting and Android assets. No paid Firebase Functions are used. The dedicated service account has only `firebaseauth.users.get`, `firebaseauth.users.update`, `datastore.entities.get/create/update` and `datastore.databases.get`. IAM permissions are database/project scoped, not per student document; Worker authorization is essential. Keep the JSON key outside the project. The existing Cloudflare secret is named `FIREBASE_SERVICE_ACCOUNT`. Never commit it or paste it into chat.

## Admin flow

Super Admin (server-issued `superAdmin: true` claim, checked against current Firebase Auth claims) and active Head Admin can select an ordinary active student → Reset password. Privileged student accounts, self-reset, mismatched Auth/profile identity and disabled accounts are rejected. Enter your own admin password for Firebase reauthentication and a 5–500 character reason. The Worker verifies Google's RSA signature, issuer/project/expiry, account revocation/disable state, recent authentication (five minutes) and the current Firestore role. Neither request-supplied roles nor CORS establish permission.

Before touching Auth, a Firestore transaction restricts the target profile, reserves a per-student operation lease and writes an audit record and actor rate counter. Authentication then receives a random temporary password and session revocation timestamp. Only after confirmation does the Worker return the temporary password once with no-store headers. Close clears the field; copy/deliver privately. Passwords never appear in audit documents, URL parameters or application logs. Only a SHA-256 digest of the high-entropy temporary password plus operation UUID is retained to reject reusing it as the personal password. The one-minute student cooldown and five resets per actor per fifteen minutes survive Worker restarts. A two-minute lease serializes resets/password completion. Request replay cannot retrieve the password.

## Student flow and enforcement

Use the usual Student ID with the temporary password in the updated website/app. The required-password modal submits a personal password to the Worker over HTTPS (not stored/logged); the existing 8–128 character policy rejects birthday/Student-ID passwords. The Worker also rejects the temporary password. Auth is updated, then another Firestore transaction clears the restriction and records completion. The client signs in again in a later second and reloads to establish fresh listeners. Gmail recovery is not implemented by this feature.

`passwordResetRequired` and `passwordResetValidAfter` are server-owned profile fields. Firestore `isStudent()` rejects restricted profiles and sessions authenticated before or at the revocation second. Students cannot directly clear the restriction or first-login flag during an admin reset. Student managers/head admins cannot edit the server-owned fields. Role promotion during a reset is blocked. Own-profile reads remain available for login/recovery. Ordinary students without reset fields retain their existing behavior. Existing initial birthday-password onboarding is unchanged. Notification/account-index/registration metadata rules retain their existing access; this is not a blanket deny of every signed-in metadata read.

## Failure handling

Firebase Auth and Firestore are not one atomic transaction. An uncertain Auth or finalization failure never reports success or releases the restriction. Wait two minutes, then an admin can issue a new reset with a new operation ID/password. If personal password completion fails after Auth changed, the new chosen password may already be active: sign in with it, wait two minutes and retry if still restricted. The audit/lease remains available to diagnose partial operations. If the temporary password was lost, it cannot be recovered; reset again. Avoid out-of-band Auth/profile/role edits while a reset is in progress. Firestore quota or Cloudflare resource limits fail closed and require retry/recovery; no unlimited-free-service claim is made.

## Deployment

Wrangler is authenticated through local OAuth. Use `npx.cmd --no-install wrangler deploy --config workers/admin-api/wrangler.jsonc`. Deploy first with `RESET_ENABLED=false`, verify health/configuration and install tested Firestore Rules, then set the flag to true and redeploy. Secret values are preserved by deployment. `/health` reports only service/enabled/configured booleans. Test forged tokens, unapproved origins and unauthenticated requests; never use a real student reset as a smoke test without choosing a test account deliberately. CORS explicitly allows local Live Server, the Firebase Hosting origins, the configured GitHub Pages origin and Android's `https://localhost`; add an actual production origin explicitly if different.

Disable new operations by setting RESET_ENABLED=false and deploying. This also disables completion, so resolve existing restrictions deliberately before a planned shutdown. Do not delete reset ledger/profile fields as a shortcut: that could revive old tokens. Rotate/revoke the service-account key if compromised. Native users need a newly built APK; old installed APKs cannot complete the protected reset flow. Do not reset a student until they can access the updated website or APK.

Validation includes signed JWT tests, role/identity/revocation checks, rate limits, replay/lease/failure behavior, temporary-password nonpersistence, and local Firestore emulator checks for reset flags, old sessions, fresh sessions and legacy provisioning. Live read-only Auth/Firestore probes verify dedicated credentials. No real student account password is changed during automated checks. Physical-device and a deliberately selected test-account walkthrough remain required for end-to-end acceptance.
