# Android attendance push notifications

The `presence-notifications` Cloudflare Worker is separate from `presence-admin-api`. Its secret is `PUSH_FIREBASE_SERVICE_ACCOUNT`, for the dedicated Google account `presence-notifications@presence-a873f.iam.gserviceaccount.com`. Never reuse or broaden the password-reset account. The current deployment has `PUSH_ENABLED=true` after dedicated IAM checks, Firestore connection checks and an FCM validation-only request passed. Rules are deployed. A physical device must still install/open the updated APK with notification permission; no real notification delivery is claimed from validation-only checks. For a new environment, start disabled until credentials and permissions are verified.

## Notification flow

Every admin event create/update atomically writes `eventPushOutbox/{eventId}` in the same Firestore batch. Both real morning/afternoon event IDs have independent schedules. Super Admin, Head Admin and Attendance Admin can queue only existing events through Rules. Arbitrary client recipients/messages are not accepted. The backend reads the authoritative event, creates a revision and schedules its milestones. Updating time/audience invalidates the old revision. Deleted events do not send. Old events do not replay notifications; existing future events should be saved once after activation to queue them.

Milestones: new event publication; ten minutes before check-in opens; check-in opening; ten/five minutes before the on-time threshold; on-time threshold reached (late check-in still available); checkout opening for students with a check-in; ten/five minutes before final cutoff; session closed for students with unfinished attendance. No late-threshold reminder is generated before the check-in window opens. Displayed remaining minutes are calculated at sending time. All schedules use the saved absolute timestamps/Philippine-time fallback.

The cron runs each minute, reading bounded pending-outbox and due-job queries. It does not scan all events each minute. Internal service-binding RPC fans out over 32 stable device shards, with pages of 25 devices and a maximum recursion depth. Each page batch-reads only the profile/attendance fields required for eligibility, then rechecks before sending. Completed records, locked/inactive profiles, expired devices and pre-reset device sessions are excluded. A removed student with an existing check-in can still receive checkout reminders. Exact-second delivery is not promised; expired jobs/messages are discarded rather than replayed after an outage.

Per-job/shard leases prevent simultaneous processing. Retried FCM sends use stable Android notification tags, replacing an existing notification rather than stacking it. FCM and Firestore cannot commit atomically: exactly-once delivery is not guaranteed if an acknowledgement is lost. One collapse key intentionally retains the newest pending attendance message for an offline device. Messages have short TTLs. Retry failures do not claim successful delivery. Invalid/UNREGISTERED tokens are deactivated. Token documents expire logically after 30 days without registration; inactive/expired records are skipped. Automatic physical deletion/retention is not enabled; configure a reviewed retention policy separately.

## APK and website

The existing Android Firebase `google-services.json` already matches the project/package. Capacitor push handles token registration, permission and background notification display. The notification channel is high importance and uses the existing monochrome attendance icon. Android settings determine sound, heads-up and lock-screen display. Tokens are registered over HTTPS using the student's Firebase ID token; the server verifies it and account revocation/disable/profile status. Device tokens are never available to Firestore clients or stored in logs. New registrations are rate-limited to 20 per student per 15 minutes.

Successful backend registration cancels legacy local attendance alarms; thereafter push supplies phone notifications and foreground in-app messages. If push registration is unavailable/disabled, existing local reminders remain the fallback. The website never requests browser push permission and retains its existing in-app reminders. Foreground FCM messages use an in-app toast, without a second phone alert. Clicking a notification opens Events under the current student session; notifications for a different user are rejected. Logout deactivates the registration and deletes the native FCM token, with token deletion still attempted if the backend is unreachable. Network failure can prevent confirmed cleanup: do not promise immediate server-side revocation while offline. The APK must be opened after installation/sign-in to establish its channel/token.

## Activation setup

1. Google Cloud project **presence-a873f**: create service account **presence-notifications**.
2. Create a custom project IAM role **Presence Notifications** (`presenceNotifications`) with `datastore.databases.get`, `datastore.entities.get`, `datastore.entities.list`, `datastore.entities.create`, `datastore.entities.update`, `firebaseauth.users.get`, and `cloudmessaging.messages.create`. If the console does not offer the last permission in a custom role, grant the predefined **Firebase Cloud Messaging API Admin** role to this dedicated account, with the other six in the custom role. These IAM permissions are project/database scoped; endpoint authorization remains necessary.
3. Assign the role(s) to the new account on the **project IAM** page. Do not grant Owner, Editor or roles on another service account.
4. Enable **Firebase Cloud Messaging API** (`fcm.googleapis.com`) in this project. Generate a JSON key for this new account and keep it outside the repo; provide only its local file path to the developer, never paste its contents.
5. Upload the JSON directly as a Worker secret `PUSH_FIREBASE_SERVICE_ACCOUNT` to `presence-notifications`. This is a separate Worker/secret; the reset backend remains unchanged.
6. Test Rules using `tests/push-notifications.emulator.cjs` alongside reset/provisioning emulator checks, then deploy the reviewed Rules. Deploy the notifications Worker disabled first; health must report configured=true. Set `PUSH_ENABLED=true` and redeploy after setup. Cron propagation can take several minutes.
7. Build/install the updated APK locally before releasing it. Test using a deliberately chosen test student/section/event; do not broadcast a test to everyone. Use future windows at least ten minutes apart to test all thresholds. Publish/edit from the updated admin website. Verify permission denial, foreground/background/locked screen, notification tap, a completed student's skipped reminder, schedule change/deletion, logout and account switch on a physical device.

Commands: `node <cached-wrangler-path>/bin/wrangler.js deploy --config workers/notifications/wrangler.jsonc`; secret command uses `secret put PUSH_FIREBASE_SERVICE_ACCOUNT --config workers/notifications/wrangler.jsonc` with JSON piped directly (never displayed). For a first deployment, Wrangler may require creating the disabled Worker without the SELF service binding once, then redeploying the checked-in config with the self binding.

No server-initiated test send or production account mutation is part of the automated tests. Unit tests mock FCM; emulator tests use `demo-presence-audience`. Monitor Firestore reads/writes and Worker resource usage before broad rollout. The cron's two empty queries cost roughly 2,880 document reads/day; each delivery additionally queries devices, reads current profiles/attendance, and writes leases/checkpoints. Large rosters and many daily milestones can exceed a Spark project's daily allowance. There is no automatic paid-plan enrollment or billing upgrade. Start with a small test cohort and measure before enabling all sections.
